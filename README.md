## 两大核心

项目长期只做两件事,不是并列,是递进:

| 核心 | 要解决的问题 | 对象 | 状态 |
|------|-------------|------|------|
| **一 · 职场人采用 AI 工具** | 个人怎么把 AI 用进真实工作,拿到可验收的产出 | 个人 | **当前内容主线**,持续打磨 |
| **二 · 借助 AI 改造组织** | 团队 / 组织怎么改流程、治理与能力,让个人提效变成组织能力 | 团队、组织 | **规划中**,见路线图 |

- 只有核心一:个人提效会被组织惯性吃掉,工具买了、账号发了,流程没变。
- 只有核心二:没有个人使用土壤,组织改造容易变成采购和培训,落不了地。
- 所以顺序是:**先把个人用透,再谈组织改造**;核心二不提前铺内容。

> 当前站点的全部内容都属于核心一。核心二先在 README 规划,等有真实案例再上线。

## 这是什么

以 **人机协同工作范式**为主线的人机协同指南,不以单一工具为中心。

- 不做「Cursor 从入门到精通」式的工具说明书
- 工具只是实现范式的载体,换工具,方法论照样成立
- **方法优先,工具为载体**:场景内容统一「方法篇(什么算好)+ 工具篇(怎么用 AI 做到)」;工具换代,方法与判断标准不换
- **任务制学习路径**:基础认知 → 工具主线 → 补充与实战;每个任务都有任务卡(产出物 / 时长 / 难度 / 验收)
- **泛职场,不按职业分轨**:面向所有想用 AI 把工作做得更好的人;写作、数据、工程只是不同的任务场景,编程只是其中一种形式
- **安全与验证横向贯穿所有层次**,不是某一章

> **术语**:推荐使用「人机协同工作范式」,而非「氛围式协同」—— 后者容易与「氛围式编程」混淆。

## 核心一:职场人采用 AI 工具(当前主线)

### 已上线

| 模块 | 内容 |
|------|------|
| **学习路径** | 基础认知 → 工具主线 → 补充与实战,每段有产出与验收 |
| **工具主线** | 4 个工具词条;WorkBuddy 10 个实战配方;Trae 8 个案例精选;[模型怎么选](docs/model-selection.md)(跨工具) |
| **实战剧本** | 周报(办公)+ 加功能 / 修 Bug / 重构(工程) |
| **方法论** | Prompt / Context / 迭代 / Review + [安全与验证](docs/safety.md) |
| **认知** | 基础认知、工具图谱、FAQ、资源 |

### 还要打磨和补充

| 优先级 | 缺口 | 具体动作 |
|--------|------|---------|
| **P0** | 办公场景剧本只有周报 | 补多文档汇总、Excel 清洗、竞品调研;每篇按「真实示例 → 10 分钟快速版 → 方法篇 / 工具篇 → 验收」 |
| **P0** | Claude Code / DeepSeek Harness 没有进阶内容 | 补实战配方与案例,和 WorkBuddy / Trae 对齐 |
| **P1** | 任务页结构不统一 | 3 个工程剧本改成「示例先行」,统一任务卡、验收和「数字 / 代码回源」要求 |
| **P1** | 案例覆盖不均 | 每个主工具至少 8 个代表性案例;案例要有「可复用的做法」,不做纯展示 |
| **P2** | 模型选择会过期 | 每季度复核一次;保留判断顺序,更新模型示例 |
| **P2** | 读者转化未验证 | 跟踪「首页任务入口 → 任务完成」路径,用真实反馈迭代首页与任务卡 |

**质量门槛**:方法篇 + 工具篇、任务卡、可回源、验收清单、真实案例链接。新内容按这个门槛验收;已上线内容按同一标准逐步补齐。

## 核心二:借助 AI 改造组织(规划中)

> 个人提效 ≠ 组织提效。组织改造要同时动流程、权限、数据、治理、培训和度量。

### 内容框架(计划)

| 模块 | 要回答的问题 | 可能的形式 |
|------|-------------|-----------|
| **1. 组织诊断** | 哪些流程值得先改? | 流程盘点表、价值-风险矩阵、AI 适用性判断 |
| **2. 试点** | 怎么用最小成本验证? | 选 1 个团队 / 1 条流程,设基线,3-4 周试点,定验收指标 |
| **3. 流程重构** | 人机怎么分工? | SOP、模板 / Skill、知识库、验收标准 |
| **4. 治理** | 怎么既放开又不失控? | 数据分级、权限最小化、审计、合规、供应商评估 |
| **5. 规模化与变革** | 怎么让组织真的用起来? | 培训体系、内部案例库、角色变化、激励、度量 |

### 路线图

| 阶段 | 做什么 | 产出 | 状态 |
|------|--------|------|------|
| **0 · 现在** | 完成核心一;同步收集组织问题 | 访谈笔记 / 问题清单 | 进行中 |
| **1 · 试点** | 3-5 个团队 / 流程改造 | 案例:现状 → 改造 → 指标 → 可复用做法 | 规划中 |
| **2 · 方法** | 把试点抽象成方法 | 组织 AI 成熟度、流程盘点模板、治理清单 | 规划中 |
| **3 · 工具** | 团队级平台落地 | Agent 平台选型、权限与审计、团队知识库 | 规划中 |

### 衡量标准

- 流程周期、返工 / 错误率、人均产出、员工负担、合规事件
- **不以「用了多少 AI」为成功标准**,以「流程结果有没有变好」为标准

### 边界

- 没有真实案例前,不写空泛的「组织 AI 框架」
- 先征集 3-5 个真实的组织改造案例,再决定内容形态
- 组织改造涉及权限、合规与人事,案例会做脱敏与匿名处理

## 5 层架构 + 2 条贯穿原则

```
第 5 层  底层基建     Agent Runtime 底座、基准评测、私有部署、团队级落地
第 4 层  进阶方法论   任务拆解、多 Agent 协同、提示词工程、MCP 生态
第 3 层  场景实践     写作 / 文档 / 数据 / 工程 / 自动化
第 2 层  工具范式     5 大类工具图谱
第 1 层  基础认知     定义、人机分工、通用底层能力

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
主线原则  方法优先,工具为载体   ← 决定每篇场景内容的写法
横向原则  安全与验证 · 结果校验   ← 贯穿以上所有层次
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**五层是内容的组织层次,不是学习顺序。** 每篇内容都标注 `prerequisites`,读者按需进入。

**站点分两层呈现**:前台是「任务入口 + 学习路径」,后台是「知识库」(基础认知 / 工具图谱 / 方法论 / 安全)。**首页先给任务,不给体系** —— 读者选一个真实任务,照任务卡做完,再回来看方法。

**内容优先的阅读外壳**:阅读页不设左侧栏,顶部导航负责全局可达;正文用面包屑 + 上一篇/下一篇维持阅读顺序,右侧只保留本页大纲。

> **与两大核心的关系**:第 1-4 层主要服务核心一(个人采用);第 5 层「底层基建」是核心二(组织改造)的主要落点,但目前内容仍偏个人工具链,团队级落地待补。

## 学习路径(三段)

只讲三段;「入门 / 熟练 / 进阶 / 专家」这套刻度不用背,完整路线与验收标准见站内[学习路径](docs/learning-map.md)。

| 段 | 你会做到 | 主要内容 | 产出 |
|----|---------|---------|------|
| **第 1 部分 · 基础认知** | 分清人机分工,知道 AI 在哪会编 | 基础认知 + 快速开始 | 一个真实的、能交付的产出 |
| **第 2 部分 · 工具主线** | 把 1-2 个主流工具练到 L3/L4 | 进阶模型 + 4 个工具练习清单 | 模板 + 避坑清单 + 自动化流程 |
| **第 3 部分 · 补充与实战** | 稳定交付、能验收、能沉淀 | 安全与验证 + 方法论 + 实战剧本 | 完整工作流 + 自己的验收清单 |

## 内容元数据

每篇内容带 frontmatter,由 `pnpm check:meta` 在构建时校验受控词表:

```yaml
type: tool | scenario | method | concept | reference | index
audience: workplace | developer | both
level: L1 | L2 | L3 | L4
status: draft | review | published
paradigm: 2.1 ~ 2.5        # type=tool 必填
prerequisites: [has:terminal, ...]
verified_at: 2026-10-20    # type=tool 必填,超 180 天提醒复核
```

**三类内容实体不互相复制**:工具资料 / 场景工作流 / 方法论资产,通过链接与元数据关联。工具更新只改工具词条一处。

> **关于 `audience`**:该字段只描述内容的典型工作场景(`workplace` = 办公场景,`developer` = 代码与工程场景,`both` = 跨场景通用),**不代表站点按人群分轨**。

## 贡献

**核心一**新增内容需满足三要素:属于 Vibe Working 范畴、能归入 5 层架构、有明确的适用场景与一个真实任务。新增文件请带合法 frontmatter,并通过 `pnpm check:meta`。

**核心二**优先征集真实组织改造案例。欢迎提供(可脱敏):

- 改造前的流程与基线(周期、人力、错误率)
- 用了哪些 AI 工具 / Agent,人机怎么分工
- 改造后的指标变化与踩过的坑
- 哪些做法可以复用,哪些只适用于你的组织

没有真实案例,核心二不写框架。欢迎 PR 或开 issue 提供线索。
