# 调试与迭代

> 第 4 层 · 系统化运用。本页讲**怎么拆、怎么恢复** —— 「为什么要拆」这个原则在 [基础认知](/concepts#为什么要拆-唯一需要记住的判断)。

> AI 不会一次做对。**重要的不是你会不会遇到错,而是你遇到错怎么应对。**

## 一句话核心

> 错了不纠正,**重来一次**。这是社区共识,也是 Anthropic 工程团队的明确建议。

## 错了不纠正,重来一次

### 为什么不能纠正

你会得到经典的:

> "您说得对,我马上改。" —— 然后 30 秒后给你另一个错的版本。

**原理**:AI 的"道歉"是模式匹配,不是反思。纠正 = 浪费一轮对话 + 污染上下文。

### 开发场景:clear + 重写

```bash
# 1. 全部回滚
git checkout .

# 2. 清 context
/clear

# 3. 重发原始 prompt + 把"避免这个错"加在后面
```

例:

```
❌ 你刚才在 user.go:142 把 nil 检查写错了,改一下

✅ (清空) /clear
请给 UserService.login 加 nil 检查。注意:
- 不要用 if err != nil 这种通用检查
- 用 if user == nil { return ErrUserNotFound }
- 加单元测试覆盖空指针场景
```

### 办公场景:同样不纠正,换个动作

你在 WorkBuddy 里让 AI 整理一份报表,它把「华东区」和「华东地区」当成了两个不同的分类项。你纠正它之后 —— 它改对了,但**语气里带着「我明白了」,格式全变了**,前面三段你满意的排版被它重排过。

**同样的道理,不同的动作**:

| 场景 | 别做 | 改做 |
|------|-----|------|
| 桌面工作台 | 在原会话里一步步纠正 | **开新会话**,重新给一次完整要求 |
| 文档处理 | 局部改来改去 | 回到原始材料,重发完整 prompt |
| 数据处理 | 让它补一张表 | **重来**,并加上「分类标准以 XX 字段为准」 |

关键那条约束是这样补上的:

```
❌ 华东区写错了,是华东地区

✅ (新会话)重新给一次:
把这份销售表按区域汇总。
分类标准:以「区域」字段的原始值为准,不要自己归并或拆分同义写法。
发现同义写法时列出来问我,不要自己决定。
```

**「不要自己决定,把问题抛回来」** 是所有场景通用的那条 —— 它把 AI 从「自主决策者」改回成「等你确认的执行者」。

::: warning 什么时候可以直接纠正
只有一种:**小的措辞调整**。「第二段再短一点」「把这个词换掉」—— 这类不涉及方向性判断的微调,直接说就行。

判断标准:**如果你需要说「不是这样,是那样」,就该重来。** 需要说「再调一点」的,可以直接调。
:::

## Plan Mode:复杂任务先规划

### 用法

按 `Shift+Tab` 进入。AI 会:

1. 先输出"将要做什么"的清单
2. **不会执行任何修改**
3. 你审 → 它再改

### 何时用

| 用 | 不用 |
|----|------|
| 改 3+ 个文件 | 单文件小改 |
| 加新接口 | 加一行日志 |
| 重构 | 改注释 |
| 跨模块联动 | 写单测 |

### 实战:Plan Mode 的标准 prompt

```
请先进入 Plan Mode,不要直接改代码。
任务:[描述]
你需要先回答:
1. 你打算改哪些文件?为什么?
2. 有没有更简单的方案?
3. 怎么验证改对了?
```

## AI "降智"的诊断表

| 症状 | 真原因 | 解法 |
|------|--------|------|
| 重复之前说过的话 | context 满了 | `/clear` |
| 答非所问 | prompt 模糊 | 重写 prompt,加 4 要素 |
| 输出越来越短 | context 满了,在"省 token" | 拆任务 |
| 反复改同一个错 | 你在"纠正"它 | clear + 重写 |
| 引入完全无关的代码 | 没指定范围 | 显式说"只改 X" |
| 自相矛盾 | context 太长忘了 | 拆短 |
| 自信地写错 | AI 不会自我怀疑,正常 | 你的验收见 [AI 产物 Review](/workflow/review) |

## 5 步排查流程

AI 输出不是你想要的时候,按这个顺序:

```
1. 我的 prompt 漏了什么?
   → 补全 [角色/任务/约束/输出格式]

2. 我的 prompt 太模糊?
   → 加具体的输入/输出例子

3. Context 是不是满了?
   → /context 看占用;超过 60% → `/clear` 拆任务

4. 是不是用错了工具?
   → 单文件小改用 Trae IDE / 跑命令用 Claude Code

5. 模型本身的限制?
   → 换模型 / 换个角度拆需求
```

## 死循环检测与解法

### 5 个信号

- 同一个错改 3 次都改不对
- AI 反复"重写"但 diff 几乎一样
- 你已经"纠正"了 2 轮以上
- AI 开始"我重新尝试..."自顾自
- 你自己都开始怀疑人生

### 解法

```bash
# 1. 立刻停手
ESC  # 中断当前生成

# 2. 全回滚
git checkout .

# 3. 完全重新开始
/clear

# 4. 拆任务到不能再拆,每个任务独立验证
```

如果还是不行,**这不是 prompt 的问题,是模型/任务本身的问题** —— 考虑:

- 换模型(Family 不同)
- 找真人问
- 任务退一步,先做能做的部分

## 迭代节奏的 5 个习惯

| 习惯 | 为什么 |
|------|--------|
| 每完成一个小目标 → `git diff` | 你能早发现、不会积压 |
| 测试驱动,先写测试 | 验证有依据 |
| commit 小且语义化 | 回滚有依据 |
| `ESC` 而不是等它跑完 | 浪费 token 还污染 context |
| `/clear` 而不是继续对话 | context 是有限资源 |
