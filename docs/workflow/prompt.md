# 怎么写好 Prompt

## 先看一个你一定遇到过的场景

你让 AI 写一份竞品分析,写回来了 —— 结构完整、措辞专业、看着挺像回事。但你拿去做汇报,发现它**没给数据来源**。

你又让它重写,它说「好的,以下是改进版本」,然后给出同样没来源的内容。

第二次之后你明白了:**问题不在模型,在你的第一句话太模糊。** 你要的是「有据可查的分析」,你说的是「写一份竞品分析」。AI 没有义务猜到哪个字重要。

这就是「AI 变笨了」最常见的原因 —— 模型没变,是你的描述不够精确。

> **本页的核心主张**:AI 不是「理解你」,是「匹配你描述最像的解」。描述越精确,输出越可用。
>
> 本页例子同时给**职场场景**和**开发场景**,四要素在两边是同一套。

## 4 要素框架

任何 prompt 都最好包含这四件事。**缺的那一项,恰恰是后面返工的原因。**

| 要素 | 作用 | 少了会怎样 |
|------|------|-----------|
| **角色** | 让 AI 进入特定视角 | 给出泛泛而谈的通用答案 |
| **任务** | 明确做什么 | 理解偏差,做出来的不是你要的 |
| **约束** | 边界 / 限制 / 风格 | 动了不该动的,写了不该写的 |
| **输出格式** | 怎么交付 | 给了一堆文字,不是你要的表格 / 文件 |

::: warning 这里没有「漏一个 +30%」这种数字
[基础认知](/concepts#幻觉-ai-会自信地编)一节明确要求:凡是具体的、可验证的事实,一律自己确认一遍。一个精确到百分比的「出错概率」如果没有来源,它就是编的 —— 不管谁写的。
:::

### 同一套四要素,两种场景

| 要素 | 职场场景 | 开发场景 |
|------|---------|---------|
| **角色** | 你是一位市场分析负责人 | 你是一位资深 Go 后端工程师 |
| **任务** | 对比 3 家竞品的定价策略 | 给 OrderService 加一个 cancel 接口 |
| **约束** | 只用公开信息;数据必须给来源;不超过 2000 字 | 只改 OrderService,不改 model;错误用 pkg/errors;加单元测试 |
| **输出格式** | Markdown 表格 + 每条结论后附来源链接 | 先列改动文件清单,再给 diff,最后跑测试结果 |

**框架完全一样,只是换了填充内容。** 这就是为什么它适用于所有场景。

## 先看清问题出在哪:5 个反模式

### 反模式 1:模糊动词

❌ `帮我优化一下这段代码`
❌ `帮我做一份分析`

✅ `把嵌套层级降到 3 层以内,函数拆到 ≤ 30 行,变量名改用业务语义命名`
✅ `对比 3 家竞品的定价策略,每条结论后必须附来源链接`

**信号词**:`优化`、`做好`、`分析一下`、`整理` —— 这些词没有可验收的标准。

### 反模式 2:缺失上下文

❌ `修一下这个 bug`

✅ `UserService.login 偶发返回 500(本地 1/50 概率),日志显示是 nil pointer。已锁定 src/services/user.go:142。请只改这一处。`

**差别在哪**:有没有**复现条件**、**已知线索**、**范围边界**。

### 反模式 3:超长 prompt

❌ 把项目背景、5 个相关需求、3 个注意事项塞一段

✅ 拆成多轮对话,先给任务再补约束

### 反模式 4:没指定输出形式

❌ `写一下单元测试`

❌ `写份竞品分析`

✅ `用 vitest,只测 happy path,断言覆盖返回值与 HTTP 状态码,放在 __tests__/login.test.ts`
✅ `Markdown 表格,列为:竞品 / 定价档位 / 核心功能 / 差异点,表格后写 3 句总结`

**最容易被忽略的一条。** 不说形式,AI 默认给一段文字 —— 而你要的是能直接用的东西。

### 反模式 5:没说验收标准

❌ `重构 User 模块`

✅ `重构 src/user/,目标是:1) 单一职责,2) 加 mock 接口,3) 现有测试不挂。重构完跑 pnpm test,贴结果。`

## 高频 prompt 模板

复制即用,改方括号内即可。**前三组两个场景都适用,后三组偏开发。**

### 1. 数据处理与清洗

```
你是 [数据分析角色]。
数据:[文件路径 / 数据来源,以及数据规模]。
任务:[清洗规则,例如去重、补缺失、统一格式、计算派生字段]。
约束:
- 不修改原始数据,输出到新文件
- 不确定的地方标注出来,不要自己猜
- 涉及删除的行,先列出清单等我确认
输出:[目标文件格式] + 一份「处理了什么」的摘要(处理了多少行、剔除了多少、哪些字段存疑)
```

::: tip 为什么这么写
「不确定的标注出来,不要自己猜」这一句能避免大部分数据类事故 —— AI 最擅长做的就是**自信地填上缺失值**。删除类操作要求先出清单,是因为原始数据不可再生。
:::

### 2. 文档撰写与润色

```
你是 [写作角色,写给谁看]。
素材:[原文 / 资料 / 会议记录]。
任务:[写什么,例如整理成汇报稿 / 润色现有文案 / 汇总成周报]。
约束:
- 只用素材里的信息,不要补充未经证实的内容
- 保留原文的关键数据和结论
- 语气 [正式 / 简洁 / 口语],长度 [字数]
输出:[格式] + 标注出所有需要你确认的事实
```

### 3. 信息提取与汇总

```
你是 [信息分析角色]。
材料:[文件 1 / 文件 2 / ...]。
任务:提取 [具体字段] 并汇总成一张表。
约束:
- 只提取材料里明确写了的,没写的填「材料未提及」
- 不要推断、不要补全
- 同一个字段在不同材料里冲突时,列出冲突并注明出处
输出:Markdown 表格 + 一段「材料覆盖不到什么」的说明
```

**这一条是职场最高频的任务**,也是 AI 最容易出错的地方 —— 它会**自作聪明地填补空白**。

### 4. 加功能(开发)

```
你是 [角色]。
任务:给 [文件路径] 增加 [功能描述]。
约束:
- 不动 [明确不要碰的文件/范围]
- 沿用现有命名/风格
- 加单元测试覆盖 [场景]
输出:先列改动文件清单 → 关键 diff → 测试结果
```

### 5. 修 bug(开发)

```
你是 [角色]。
Bug:[现象描述 + 复现步骤 + 期望 vs 实际]。
定位:[已经知道的原因 / 已排除的可能 / 相关代码行号]。
任务:最小修复方案。
约束:
- 只改必要的行
- 加一个回归测试
- 解释为什么这么修
输出:改动 diff + 测试结果 + 一句话总结根因
```

### 6. 重构(开发)

```
你是 [角色]。
范围:[文件/模块]。
目标:[可量化的目标,如"圈复杂度 ≤ 10 / 行数 ≤ 200"]。
前置:已覆盖测试是 [测试覆盖率 / 测试文件路径]。
任务:重构 + 保持测试全绿。
约束:
- 不改对外接口
- 行为零变化
- 每步跑测试
```

### 7. 代码 review(开发)

```
你是 [角色]。
对 [commit / 文件路径] 做 Code Review,5 个维度:
1. 正确性(边界、并发、错误处理)
2. 性能(热路径分配、N+1)
3. 安全(注入、鉴权、信息泄露)
4. 可读性(命名、结构、注释)
5. 可测性(是否能加测试)
输出:每维度用 "严重 / 建议 / 不错" 三档评级 + 至少一个具体例子。
```

## 60 秒走一遍:真实场景

拿最常见的「整理会议纪要」过一遍四要素怎么落地。

**原始需求**(❌ 反模式 4 + 5):

```
帮我整理一下今天的会议
```

AI 会回你一大段流畅的总结,但:**哪些是决议?哪些是个人发言?谁负责什么?** 全都混在一起,你还得二次阅读。

**加上四要素**(✅):

```
你是会议纪要整理员。
素材:粘贴的会议记录(见下)。
任务:整理成一份可发出去的会议纪要。
约束:
- 只用记录里明确写的内容,不补充任何推测
- "待确认"的信息单独列一节,不要混进结论
- 每个待办事项后面标上负责人和时间,记录里没写的标"未指定"
输出:
1. 会议概要(3 句以内)
2. 决议清单(每条一句话)
3. 待办事项表(事项 / 负责人 / 截止时间)
4. 待确认信息(记录里模糊或不完整的部分)
```

**差别在哪**:第四节「待确认信息」是关键 —— 它让 AI 把不确定的东西**显式交还给你**,而不是自己填平。这是职场场景里最重要的一条防御。

## 让好 prompt 可复用

同一类任务反复写,就该沉淀下来。三种载体:

| 载体 | 适合 | 写在哪 |
|------|------|-------|
| **项目规则文件** | 项目级长期约定 | `CLAUDE.md` / `AGENTS.md` |
| **提示词模板** | 反复做的同类任务 | 本页的模板区 |
| **Skills / 工作剧本** | 多步骤固定流程 | 独立文件 |

**项目规则文件**是性价比最高的一个 —— 写好之后 AI 第一轮就能给出贴合规范的产物,不用每次重复交代:

| 段落 | 该写什么 |
|------|---------|
| 项目背景 | 一句话:技术栈 + 业务领域 |
| How to run | install / dev / test / lint 一行一条 |
| 协作规则 | Plan Mode / 小改动 / 测试覆盖 / 禁止项 |
| 验收标准 | 跑通哪些命令算完事 |
| 风格 | 命名、错误处理、库选择偏好 |

写得好的规则文件,能让 AI 在完全没看过项目的情况下,第一轮 prompt 就给出可用的结果。

## 自检清单

发 prompt 之前过一遍:

- [ ] 角色给了吗?
- [ ] 任务有**可验收的标准**吗?(不是「做好」,是「降到 3 层以内」)
- [ ] 「不要碰什么」写了吗?
- [ ] **输出形式**说清了吗?(表格 / 文件 / 清单,别让它默认给段落)
- [ ] 该引用的上下文显式引用了吗?
- [ ] 数据类任务:要求它**标注不确定的地方**了吗?

**最后一条是职场场景最容易被忽略的。** AI 会把缺失的信息填得很像真的 —— 不主动要它标注,你就得自己一条条核。
