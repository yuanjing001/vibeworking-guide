# AI 产物 Review

> AI 写得快,也会自信地写错。**Review 不是可选项,是 AI 协作的标配。**
>
> 本页分两部分:**代码方向**的深度校验,以及**所有场景通用**的验收原则。执行前后安全清单见 [安全与验证](/safety)。

## 为什么必须 Review

AI 有 4 个"看不到"的盲点:

1. **业务上下文**:它不知道产品真正在意什么
2. **历史包袱**:它不知道以前为什么这么写
3. **运行时行为**:它写出来没真跑过、没压测过
4. **信息来源**:它无法区分「材料里写了」和「它觉得合理」

**它会自信地写出语法完美、但结论错误的内容。** 第 4 条在办公场景里危害最大 —— 一份读起来很有说服力的报告,如果数据是编的,发出去就收不回来了。

## 通用验收:三条铁律(适用所有场景)

不管你用哪个工具、做什么任务,验收前先过这三条:

| # | 铁律 | 具体做法 |
|---|------|---------|
| 1 | **数字必须自己核** | 抽查 N 条,和原始数据对一遍;行数对得上吗? |
| 2 | **来源必须能打开** | 让它给出处;点开验证,链接是真的吗? |
| 3 | **对照原始需求** | 你的要求逐条打勾,有没有漏项? |

**为什么这三条不能省**:AI 最擅长的是把「不知道」填充成「听起来很合理」,而且填充得毫无痕迹。

### 办公场景的高频造假点

| 位置 | 它会怎么编 | 怎么查 |
|------|-----------|-------|
| 数据表格 | 补全缺失值、推算没有的数 | 抽查 3-5 行,回原始文件核对 |
| 调研报告 | 给出不存在的链接或来源 | 逐个点开,链接打不开就是编的 |
| 时间线 | 把「大概同期」写成具体日期 | 回原始记录核对 |
| 表格合计 | 加总错误(自己算一遍) | Excel 里重新求和 |
| 引述 | 把你的原话改写成书面语 | 关键引述逐字核对 |

::: danger 最危险的一种
不是明显错的数字,而是**格式整齐、看起来专业、但依据不明**的数字。越是这种,越容易在不核对的情况下直接发出去。
:::

## 代码方向的深度校验

下面这一节针对代码场景。

### 5 维 Review 清单

| 维度 | 关键问题 |
|------|---------|
| **正确性** | 边界条件?空指针?异常分支?并发? |
| **性能** | 热路径分配?N+1 查询?大循环内 IO? |
| **安全** | 注入(命令/SQL/XSS)?鉴权绕过?敏感信息泄露? |
| **可读性** | 命名?函数长度?嵌套层级?注释是否解释 why 而非 what? |
| **可测性** | 能否加测试?有没有硬编码依赖时间/网络/全局状态? |

### 用 AI 帮你 Review AI

不要自己一行一行看 —— 让 AI 自己先过一遍:

```
你是 [资深角色],对 [文件/commit] 做严格 Code Review。
每维度按 严重 / 建议 / 不错 三档评级,每条都要:
- 指明文件 + 行号
- 给出具体修复建议
- 严重问题必须给可执行代码示例
```

例:

```
你是 Go 资深工程师,对 commit abc123 做 Code Review。
维度:正确性、性能、安全、可读性、可测性。
输出:Markdown 表格,每条带行号 + 修复建议。
```

## 危险信号表(必看)

| 信号 | 含义 | 行动 |
|------|------|------|
| `any` / `interface{}` 大面积出现 | 类型没想清楚 | 自己重写或换模型 |
| 跨多文件大改没有测试覆盖 | AI 在赌 | 拒收,先要测试 |
| 函数 > 100 行 | 逻辑耦合 | 让 AI 拆 |
| 用了 deprecated API | 模型知识有延迟 | 自己查文档确认 |
| 复制粘贴风格代码 | AI 在"凑" | 让它 DRY |
| 没处理 ctx.Done() / cancel | 上下文没透传 | **必查**(Go) |
| SQL 拼接字符串 | 注入风险 | **必查** |
| 没校验用户输入 | XSS / 命令注入 | **必查** |
| 新增依赖没解释 why | 加了不必要的依赖 | 拒收 |
| 注释解释的是 what 而非 why | 没理解 | 重写 |

## 3 个最小可执行 Review 动作

### 1. 看 diff,再跑测试

```bash
git diff --staged
git diff --staged | claude -p "review 这段 diff,关注正确性 + 安全"
pnpm test
```

### 2. CI 自动化 Review

在 GitHub Actions 加一个 Claude Code Review 步骤(详见官方文档):

```yaml
- name: AI Code Review
  run: |
    git diff origin/main..HEAD | claude -p "review 这段 diff"
```

### 3. 关键路径人工 + AI 双审

支付、权限、数据删除这类**不可逆**操作:

```markdown
# CLAUDE.md 规则
涉及 payments / auth / delete 的改动:
- 必须人工 review
- 必须有专门测试
- 不允许 AI 自动 commit
```

## Review 的 4 个时间点

| 时机 | 做什么 |
|------|--------|
| **改之前** | 审 AI 的 Plan Mode 输出 |
| **改之中** | 单文件小改动后立刻看 diff |
| **改之后** | 跑测试 + AI Review + 自己 spot check |
| **合之前** | PR 流程里至少 1 个人审 |

## 写给团队:Review 文化

- **Review 不等于信任危机**:对 AI 和对人一样,要审
- **越自动化的流程越要审**:Agent 自动写的越多,Review 越要严
- **重大决策不交给 AI**:架构、删数据、改 schema,你来
- **Review 沉淀到 CLAUDE.md**:每次踩的坑,顺手写进项目规则

## 自检清单

每次 AI 改完代码后:

- [ ] 看 diff 了吗?
- [ ] 跑了测试吗?
- [ ] 危险信号表过一遍了吗?
- [ ] 关键改动让另一个 AI review 了吗?
- [ ] 不可逆操作人工介入了吗?
