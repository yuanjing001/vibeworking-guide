# 基础认知

> 第 1 层 · 全员必修。这一层不绑定任何具体工具,长期稳定。**不理解这一层,后面所有工具都是白学。**
>
> **本页只讲「原则」,不讲「怎么做」。** 系统化方法在第 4 层。

## Vibe Working 是什么

**Vibe Working(人机协同工作范式)= 人主导方向与判断 + AI 承担执行与探索 + 多轮持续迭代共创**

> **术语说明**:对外描述时用「**人机协同工作范式**」或「与 AI 持续迭代的工作方式」,比「氛围式协同」更准确 —— 避免与「氛围式编程」混淆,也更贴合这套做法强调的目标控制与质量验收。

它和「单次 AI 问答」有本质区别:

| 维度 | 单次 AI 问答 | Vibe Working |
|------|------------|--------------|
| 回合数 | 一问一答就结束 | 多轮来回迭代 |
| 谁定方向 | AI 生成什么就是什么 | 人先定目标、边界、标准 |
| 产出 | 一段文字 | 可交付成果 + 可复用流程 |
| 人的角色 | 提问者 | 决策者 + 验收者 |

**一句话自检:这一轮里,谁在做判断?**
全程只有 AI 在判断 —— 那不叫协作,叫甩锅。

## 三大特征

### 1. 人主导,AI 执行

判断权在人手里:目标是什么、边界在哪、什么算「做对了」。
AI 承担的是**信息处理、草稿生成、批量操作、逻辑校验**这些执行量大的活。

### 2. 多轮迭代

第一版几乎不会是终版。Vibe Working 的正常节奏是:

```
人给目标 → AI 出草稿 → 人审 → 人指出问题 → AI 改 → … → 人验收
```

**关键认知**:迭代不是「问得更仔细」,而是「审得更具体」。你审的方向错了,迭代再多轮也是在偏。

### 3. 可复现

做对一次,要能重复做对。这靠的是把过程沉淀成 prompt 模板、检查清单或项目规则文件,而不是靠你下次记得。

沉淀的载体见 [方法论层](#沉淀载体)。

## 人机分工原则

同样一件事,谁做?按这张表分:

| 环节 | 归谁 | 为什么 |
|------|-----|-------|
| 定目标、定验收标准 | **人** | 只有你知道什么算「做对了」 |
| 判断信息真假 | **人** | AI 会自信地编 |
| 定边界(不碰什么) | **人** | AI 默认什么都能碰 |
| 批量执行、改文件、跑命令 | **AI** | 人做慢且易错 |
| 生成草稿、列方案 | **AI** | 人做慢且容易陷进细节 |
| 逻辑校验、找矛盾 | **AI** | AI 擅长穷举,你容易漏 |
| 最终验收与担责 | **人** | 责任不可外包 |

**反模式**:把「验收」也交给 AI。你让 AI 自己检查自己刚写的代码,它只会说「看起来没问题」。

## 方法优先,工具为载体

工具解决「做得多快」,方法解决「做得多好」。两者都重要,但顺序不能反。

```
好的产出 = 你的专业判断 × AI 的执行能力
```

工具是放大器:判断对了,它放大成果;判断错了,它放大返工。

| 问题 | 谁来回答 | 答错的后果 |
|------|---------|-----------|
| 这件事的「好」标准是什么 | 人 | AI 只能按模板凑一个「看起来完整」的结果 |
| 哪些环节必须我把关 | 人 | 该审的没审,错的直接交付 |
| AI 交出来的东西凭什么验收 | 人 | 把「像模像样」当成「正确」 |
| 素材整理、初稿生成、排版润色 | AI | 人做慢,且容易陷进细节 |

**一个可操作的自检**:让 AI 做任务前,先写下三句话 —— 目标是什么、好结果长什么样、什么算不合格。写不出来,说明还没到用工具的时候。

### 三个高频误区

| 误区 | 真相 |
|------|------|
| 有了办公 Agent,周报 / 方案 / 报告就能自动生成 | Agent 省掉的是整理、成稿、排版的体力活;写什么、什么算好、风险怎么报,仍然只能由人判断 |
| 工具越强,产出越好 | 工具放大的是你的判断;判断错了,效率越高偏得越远 |
| 学会工具用法 = 学会工作 | 工具用法随版本过期,「怎么定义好结果」才是可迁移的能力 |

职场场景的第一个完整示范见 [实战剧本 · 写好一份周报](/playbook/weekly-report) —— 方法篇先讲「什么才算好」,工具篇再讲「怎么用 AI 做到」。

**工具会过时,判断标准不会。** 职场场景因此统一采用「方法篇 + 工具篇」双层结构。

## 通用底层能力

这五条能力跨工具、跨人群通用。工具会换,这五条不会。

**本层只让你知道「为什么要这样」;「怎么系统地做到」在第 4 层。**

| 能力 | 本层(理解原则) | 第 4 层(系统化运用) |
|------|--------------|-------------------|
| 任务拆解 | 一次失败要全部重来 = 任务太大 | 依赖拆解、迭代规划、失败恢复 |
| 提示词 | 目标 + 上下文 + 约束 + 输出格式 | 可复用模板、质量门槛、系统提示词 |
| 结果校验 | AI 输出必须验证 | 测试设计、交叉验证、验收机制 |
| 多 Agent | 单 Agent 与多 Agent 的差别 | 分工、协调、上下文传递、冲突处理 |
| 安全 | 存在权限与泄露风险 | 最小权限、审批机制、审计流程 |

> **本层要记住的就一句话:AI 的输出默认不可信,必须由人验收。**

### 为什么要拆(唯一需要记住的判断)

> **如果一次失败,你得全部重来 —— 说明任务太大,应该拆。**

怎么拆、拆成什么粒度、失败后怎么恢复,见 [调试与迭代](/workflow/iteration)。

### 提示词的四要素

任何 prompt 建议包含:**角色、任务、约束、输出格式**。缺一个,返工概率显著上升。

```
你是 [角色]。
任务:[具体做什么]
约束:[不要碰什么 / 验收标准]
输出:[要什么形式,怎么交付]
```

完整模板库与反模式见 [怎么写好 Prompt](/workflow/prompt)。

### 幻觉:AI 会自信地编

AI 会**用完全自信的语气说出不存在的事实**。四类高发:

| 类型 | 表现 | 对策 |
|------|------|------|
| 编造 API / 文件 | 引用了不存在的方法或路径 | 让它先列出来源,你确认存在 |
| 编造数据 | 给出「根据统计」的假数字 | 数据必须来自你给的输入 |
| 编造来源 | 引用不存在的链接或文档 | 要求给出处,自己核实 |
| 过度自信 | 「这是最优雅的方案」 | 要求给 trade-off,而不是给最优 |

**通用判据**:凡是**具体的、可验证的事实**(API 名、文件路径、数字、引用),一律自己确认一遍。

完整的风险清单与防御方式见 [安全与验证](/safety)。

## 五类 Agent 范式总览

分类不按厂商,按**形态与能力边界**:

| 类 | 形态 | 判断核心 | 适合的任务 |
|----|------|---------|-------|
| **2.1 CLI 编码 Agent** | 终端 | 终端交互与代码任务工作流 | 终端、脚本与代码任务 |
| **2.2 AI 原生 IDE** | 独立编辑器 | 编辑器内的项目级开发协作 | 编辑器内跨文件改动 |
| **2.3 成品办公 Agent 工作台** | 桌面应用 | 预制办公任务与交付工作流 | 文档、表格、汇报、调研 |
| **2.4 多模型聚合通用 Agent** | 桌面应用 | 通用工作台形态与模型接入机制 | 通用工作台、多模型 |
| **2.5 Agent Runtime 底座** | 框架 / 运行时 | 是否面向 Agent 运行、编排与定制开发 | 自定义 Agent、编排与部署 |

> 同类工具的模型选择逻辑可以合并看:[模型怎么选:7 个场景 + 5 个判断问题](/model-selection)。

### 判定规则

1. 终端交互 + 代码任务工作流 → **2.1**
2. 编辑器内的项目级开发协作 → **2.2**
3. 预制办公任务与交付工作流 → **2.3**
4. 通用工作台形态 + 模型接入机制 → **2.4**
5. 面向 Agent 运行、编排与定制开发 → **2.5**

### 两个容易误判的边界

**「可改内核」不是 2.5 的唯一判据。**
有的 Runtime 并非所有组件都能自由替换,但依然提供程序化的 Agent 构建与执行接口。判据是**设计目标 + 执行模型 + 可编程边界**,不是「能不能改某个文件」。

**「支持 MCP」≠「能自定义 Agent」。**
MCP 是连接模型与外部工具 / 资源 / 提示模板的**协议机制**。接了 MCP,不代表你能改 Agent 的调度循环、状态管理或运行时。

### 不作为分类依据的因素

是否开源、是否支持聊天、是否接入某一家办公平台、是否支持某个模型、是否有图形界面 —— 这些是**属性**,不是**分类依据**。

## 沉淀载体

同一个经验重复用第三次,就该沉淀成载体:

| 载体 | 是什么 | 适合 |
|------|-------|------|
| **项目规则文件** | `CLAUDE.md` / `AGENTS.md`,启动时自动加载 | 项目级长期约定 |
| **提示词模板** | 可复制的 prompt 骨架 | 反复做的同类任务 |
| **Skills / 工作剧本** | 打包好的 SOP | 多步骤固定流程 |
| **MCP 插件** | 接入外部工具与数据源 | 需要 AI 读写外部系统 |

**项目规则文件**是性价比最高的一个 —— 写好之后 AI 第一轮就能给出贴合项目规范的产物,不用每次重复交代。最小模板:

```markdown
# CLAUDE.md

## 项目
- 技术栈:...
- 启动:...
- 测试:...

## 协作规则
- 改之前先解释思路
- 优先小改动 diff
- 跑通测试再收尾

## 禁止项
- 不动 <文件/目录>
```

MCP 与 Skills 的接入顺序建议见本篇末尾的 [技术概念速查](#技术概念速查)。

## 技术概念速查

> 这一节是**术语表**,只解释词怎么用。属于第 4 层进阶方法论的入口,详细原理在后续内容中展开。

### Agent(智能体)

能读文件、拆任务、调工具、按规则迭代完成目标的 AI 助手。关键不是模型多强,而是两点:**你给它的规则** 和 **你对产物的审核方式**。

### MCP(Model Context Protocol)

一套开放协议,让 AI 客户端用统一方式连接外部工具与数据源。

| MCP 服务 | 用途 |
|---------|------|
| `filesystem` | 读/写文件 |
| `github` | 读 PR、Issue、代码 |
| `fetch` | 抓网页内容 |
| `notion` | 读写 Notion 页面 |
| `postgres` / `sqlite` | 查数据库 |
| `puppeteer` | 浏览器自动化 |

**接入顺序建议**:

1. 先不接 MCP,把「读内容 / 改内容 / 验证 / 审产物」练熟
2. 再只接一个最安全的(比如 `filesystem`)
3. 最后才接有写入 / 网络 / 数据库权限的,每接一个就验收一次

### Skills / 工作剧本

可复用的任务模板,把「经常做的事」标准化。多人协作时,它就是团队的「AI 工作手册」。

| 场景 | Skill 示例 |
|------|-----------|
| 系统化排查 bug | `debug-investigation` |
| 发版流程 | `release-checklist` |
| 写周报 | `weekly-summary` |
| 做 Review | `code-review-checklist` |

### 项目规则文件

项目根目录下的「协作合同」,工具启动时自动读取。

| 文件 | 谁会读 |
|------|--------|
| `CLAUDE.md` | Claude Code |
| `AGENTS.md` | 通用 / Trae 等 |
| `GEMINI.md` | Gemini CLI |

### Context(上下文窗口)

AI 一次能「看见」的内容上限,本质是 AI 的工作记忆。**对话变长会被占满,到 60% 后能力下降明显**。管理方法见 [上下文管理](/workflow/context)。

### Permission / Sandbox

AI 能对你的系统做什么的限制。**跨工具的完整安全清单见 [安全与验证](/safety)。**

| 工具 | 权限模型 |
|------|---------|
| Claude Code | 默认询问危险操作;`/permissions` 设白名单 |
| Trae IDE | 默认 sandbox 内跑文件读写,网络/系统命令需手动授权 |

**新人原则:先全询问,跑顺了再放宽。**

### Plan Mode

只规划、不执行的能力。适合复杂任务先对齐方案,再动手。详见 [调试与迭代](/workflow/iteration)。
